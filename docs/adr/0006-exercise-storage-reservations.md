# ADR-0006：Java 统一单场 512 MiB 存储预算与 Go 有序计量快照

## 背景

每场演练同时产生两类持久数据：PostgreSQL 里的业务/AI 对话与工具记录（Java 拥有），以及磁盘上的工作区多版本文件、测试副本与日志（Go 拥有）。两者必须共享同一笔 **512 MiB** 单场总额度，否则无法防止某一方耗尽存储导致演练无法收尾。

## 备选方案

- **跨服务分布式事务 / 两端各自独立硬配额**：分布式事务耦合过高；独立配额则无法精确控制总和上限，且会误伤收尾阶段。
- **Java 统一预留账本 + Go 有序占用快照**：操作执行前先在 Java 事务内预留额度，副作用收敛并拿到 Go 带 `meterEpoch` 与单调序号的后置占用快照后统一结算。

## 决策与代价

选择 **Java 统一预留账本 + 256 MiB 收尾保护预留**：

- **收尾空间保护**：512 MiB 中明确划出 **256 MiB** 给冻结、最多 3 次最终验收尝试（每次 56 MiB）及安全停止元数据，普通开发/AI 消费最多使用其余 256 MiB。
- **乱序防护**：Go 快照带 `meterEpoch` 和递增序号，乱序到达的旧快照不会把账本往小里扣减。
- **阶段 6 演进（轻重准入分流，消除热路径扫盘）**：V1 将所有 40+ 个业务动作（包括问面试官、Copilot 只读工具、审批切换、获取页面凭证等 1KB 级轻操作）统一在准入前同步调用 Go `MeasureExerciseStorage()` 扫描磁盘，放大了锁争用与轻交互延迟。V2 保留联合账本与 `meterEpoch` 骨架，拆分为：
  1. **轻交互热路径**：零跨进程扫盘，直接基于 Java 持久化的最近一次 Go 计量快照 + 增量预留完成 $O(1)$ 准入；仅在预估总占用达到高水位线（如 80%）或超额触发回收重试时才回退调用 Go 真实测量校准；
  2. **重磁盘操作**（准备、受控测试、Bash/PTY 命令、回收结算）：继续执行真实计量与结算；配合 Go 侧本地 CAS Blob 去重，从根源降低磁盘写放大。
- **代价**：轻交互在低于高水位线时依赖缓存快照与保守预留（而非每次实时全盘扫描），换取了交互热路径零跨服务扫盘延迟，同时不牺牲收尾保护池的确定性。
