# 首期 Copilot 使用 LangChain4j 模型 API 与应用自管 Loop

用户在完成官方资料调研和三轮一次性 PoC 后确认：首期由 Java 应用管理 Copilot 工具循环，LangChain4j 提供模型适配，暂不引入 agentic。我们已经需要掌握 Patch、审批、工具批次、执行位置和恢复状态；本次 agentic 实现仍保留这些应用职责，尚未证明额外工作流层对首期有足够收益。当前有效职责边界见 [设计文档](../design/copilot-loop.md)。

## 考虑过的替代方案

- **AI Services 自动循环**：已验证基本审批可以通过自定义执行器实现，不能因“框架不支持审批”而排除；其原循环的透明跨进程恢复未验证。本次未选作 Copilot 主执行器，不代表禁止在其他适合场景使用。
- **agentic 工作流**：已验证实验性发行版支持工作流审批点跨 JVM 恢复；第三轮采用它包裹应用执行器，批次和消息配对仍由应用管理。暂不承担这层运行时与实验性 API 的集成成本。
- **Spring AI / Pi / 其他 Agent SDK**：已做资料调研，未做同等运行对比；不据此宣称能力或性能劣势，也不为首期新增语言运行时或替换已确认技术路线。

## 代价与复议条件

自管 Loop 意味着团队承担流式处理、工具消息配对、停止条件、持久化与故障恢复的正确性责任；它不会天然更安全，也不是自研通用 Agent 框架。选型时的 PoC 没有验证执行中途崩溃或真实模型与沙箱闭环；这是历史实验的边界，不是当前实现缺口。后续正式恢复及真实链路证据见 [第二阶段验收](../../.scratch/copilot-loop/issues/22-stage-acceptance.md)，不反过来把 PoC 写成正式实现。

如果出现多个明确的长期等待/恢复工作流，或固定版本的框架能在减少应用状态管理的同时满足相同故障场景，应重新比较。改变本决策须获得用户确认并更新设计，而不是让原型或依赖升级隐式改变架构。
