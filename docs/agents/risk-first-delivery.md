# 风险优先的实施顺序

用于跨进程副作用、异步授权和持久化恢复任务。目标是在最小链路上暴露一致性问题，减少功能铺开后的返工；本文件规定实施过程，业务状态与协议仍以 `docs/design/` 为准。

## 1. 将验收条件映射到失败场景

在现有任务 Comments 或验证记录中追加简短表格：

| 验收条件 / 不变量 | 权威状态与提交点 | 失败或竞态 | 可观察结果 / 测试入口 |
|---|---|---|---|

按涉及的分支检查：

- 跨进程副作用：重复与迟到请求、提交前后断线、回执丢失、未知结果如何确认。
- 异步授权：派发至提交之间的撤销、过期、账号或实例切换；旧结果如何隔离。
- 持久化恢复：重启、损坏或不可访问的数据、清理失败；持续失败是否阻塞其他工作。

**完成条件：** 每项验收条件都有测试入口；每个适用分支都有权威依据和可观察预期。不适用的分支注明原因，待决项按项目规则确认。复用原任务与设计链接，不另建一套规格。

## 2. 先打通最危险的纵向切片

选择一个失败后可能破坏授权、已提交数据或恢复能力的场景，使用实际边界跑通“受理 → 副作用 → 断线/撤销 → 查询或恢复”。只建立该链路需要的接口、存储与最小调用入口，随后扩展页面和其余功能。

缺陷测试先证明因目标缺陷而失败；编译、环境或夹具错误修正后重新确认红灯。

**完成条件：** 该切片的正常与故障路径均有实际测试结果；未知结果保持未决，确认成功有权威证据。仍依赖替身的跨进程行为明确列为未验证。

## 3. 分层反馈与收口

- 每个改动先运行能覆盖其风险的最小测试集；通过后再扩大验证范围。
- 完整套件用于可提交阶段收口。其后改动按影响重跑相关验证；仅在存在跨层影响或验收要求时再跑全套，记录选择依据。
- 测试通过后逐项核对第 1 步的表格；已获用户授权的独立评审按约定执行，测试结果不替代评审。

**完成条件：** 本次交付的验收项均有通过证据，未验证边界另列；阻断性发现已修复并复核。原子提交沿用根规范。

## 4. 遇到扩大返工时重定界

评审发现缺失的跨层机制，或修复新增状态、协议、迁移时，先更新失败场景表，说明影响范围及下一条可验证切片，再继续编码。出现同类问题反复返工时，检查相邻不变量，而不只修当前复现。

**完成条件：** 新发现已映射到现有验收或明确的范围变更；涉及范围扩展或待决项时已取得确认。进度报告说明当前阻断、已有证据及下一验收门槛，不把尚未验证的工作称为“只剩收尾”。
