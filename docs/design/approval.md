# 演练审批设计

状态：ASK/AUTO、steer 与约定恢复竞争已完成第二阶段验收，见 [阶段记录](../../.scratch/copilot-loop/issues/22-stage-acceptance.md)。审批是授权策略，不改变文件、命令、网络或资源权限；此结论不表示验证了所有可能的跨服务故障组合。

## 模式与提案

- 演练支持 `auto` 与 `ask for approve`，未指定时默认后者。模式仅由用户选择，变化保留审计记录；模型不能自行开启 `auto`。
- `auto` 仅免除 AI 修改提案与开发命令的逐次人工批准，不扩大工具权限。读取/搜索/受控测试在两种模式均无需逐次批准；允许范围内文本文件创建、修改、删除和原子重命名在默认模式需整批批准，在 `auto` 下校验通过后自动应用。
- 两种模式均禁止跨演练/路径越界、修改权威验收测试、宿主 shell、绕过命令工具的执行、读取模型 Key 或修改个人 Skill 原件。Docker 内开发 Bash 可联网下载依赖，仍受执行限额、可写副本与原授权同步约束。自动应用同样检查有效授权、基线、容量和演练状态，不提供自动合并或绕过沙箱的通道。
- 读取、搜索和受控测试无需逐次审批，但仍受权限和资源限制。
- AI 修改登记为带工作区基线的提案；`auto` 校验通过后应用，审批模式接受后才应用。两者均保留 Diff、结果与审计。
- 一个多文件提案整批接受或拒绝，不提供逐行/逐文件部分批准。原子性及版本见 [工作区与执行](workspace-execution.md)。
- 人工批准与模式切换检查身份、演练归属和页面操作权；自动批准使用原父任务的有效授权与登记模式版本，不保存或伪造浏览器凭证。两者都检查提案状态、生命周期、基线与容量，沿用原 FILE_BATCH；页面操作权见 [接口与事件](api-events.md)。

## 开发命令审批

- `bash(expected_revision, command, directory)` 登记原命令、项目相对目录、基线及 ASK/AUTO 模式版本；命令最多 4096 UTF-8 字节，目录最多 1024 字节。ASK 明示具体内容后等待批准，AUTO 由既有有界 worker 池处理，不由浏览器 GET 触发。
- 批准只授权该命令，不预先批准未知文件 Diff。批准、子命令意图与 `WAITING_COMMAND` 在同一事务提交；实际执行复用手动 Bash 的命令协调器，不重放 Start。即使请求键和载荷相同，也不认领已有独立手动命令。
- 新的显式 ASK 决定可授权原待审批任务继续；重读/同键重试回执不续授权、不复活已停止任务。AUTO 始终检查原父任务授权及登记模式版本；旧 ASK 不因模式切换自动批准。
- 拒绝可附最多 2048 UTF-8 字节理由，回填原调用后继续模型；同一已生效目标、基线、命令与目录的已拒内容不再登记。忙、准入失败、非零退出及同步冲突均有结构化回执，不将它们变成隐式重试。
- 父任务停止只联动持久绑定的命令。进程静默、同步结论与清理均收敛后才回填并结束父任务；同步冲突/拒绝保留候选变化，不假称代码已写入。steer 使未批准命令失效，已经受理的命令先完成核对再处理新方向。

## 模式切换

以服务端登记提案为生效分界：提案按登记时模式处理；模型已开始生成但尚未登记的提案，使用登记时最新模式。

已登记的待审批提案不会因切到 `auto` 自动获批。切换和登记必须有确定顺序；前端收到切换成功后才展示生效状态。

## 操作语义

| 操作 | 含义 |
|---|---|
| 停止任务 | 停止 Copilot 后续执行，保留已生效结果 |
| 拒绝修改 | 当前提案不应用，回填拒绝结果；Copilot 可以继续调整 |
| 撤销修改 | 恢复已应用代码；首期不提供此能力 |

拒绝可附理由，不使整轮任务自动失败；模型不能原样反复提交被拒方案。停止显示“正在停止”，待执行结果收敛后显示“已停止”与已应用修改，不将未知写入伪报为未应用。Loop 与 steer 见 [Copilot Loop](copilot-loop.md)。

## 失效与竞争

- 基线不匹配即使提案失效，不自动合并；重新读取、生成新提案，旧批准不授权新内容。
- 不设独立审批倒计时。工作区变化、所属任务停止、steer 使旧计划失效、演练结束或清理会终止旧审批的可处理性。
- 演练内显式切换模型本身不使待审批提案失效，也不自动批准/拒绝；当前请求及工具批次按原规则处理，下一次模型请求才使用新模型。模型切换与审批模式切换是不同操作，不绕过上述失效条件。
- 批准、停止、steer 及到期收尾按服务端确定顺序处理：停止/失效先生效则禁止写入；修改先应用成功则保留，不自动回滚。
- 已在执行的写入须对账后给出终态，不能仅凭按钮点击时间认定结果。
- 待审批任务可在重启后恢复，处理前重新校验权限、基线与状态，不自动批准。

## 持久实现与验证边界

- 缺省 ASK / 模式版本 0。模式确认要求 ACTIVE、当前操作权、期望版本与幂等键；同值确认也增加版本并审计。确认、提案登记和自动准入共用资源所有者锁确定顺序。
- V32 保存当前模式及每次确认的 actor、授权版本、原请求键/指纹、前后模式和时间；模式审计纳入统一容量与演练删除。读取返回最近 20 条，按数字版本倒序；容量不足不改变模式，停止和结束能力仍保留。
- 提案保存登记模式及模式版本。旧 ASK 不被新 AUTO 自动批准；已登记 AUTO 不因切回 ASK 改写授权。AUTO 不接受手动决定。
- 登记释放 worker；已有有界 worker 池执行自动准入，计量 RPC 和完整批次解码在事务外。自动决定、原 FILE_BATCH 绑定和 WAITING_WRITE 同事务；恢复只使用原操作及回执，不重复创建批次。
- 确定的容量/基线等失败保留 Diff 与结果；5xx 计量/协调故障保留原待处理提案，不伪造拒绝后再收费请求模型。停止、到期或原授权失效先落盘则不写入；已确认应用不回滚。
- 确定性 PostgreSQL 测试覆盖登记/确认顺序、并发版本冲突、授权失效、原回执丢失和服务实例重建；它们不等于真实 JVM 强杀矩阵。真实供应商双浏览器验证覆盖默认审批、AUTO 应用、草稿保留、切回 ASK 和 GET-only 重载。恢复竞争证据已由 P2-14 收口，包括按需真实强杀场景；不将单测重建实例当强杀，也不作跨系统 exactly-once 承诺。

## 验收要求

覆盖默认模式、登记与切换竞争、旧提案保留、拒绝后继续、重复批准、越权、版本变化、多文件失败、停止/steer/到期与批准竞争及重启恢复。使用可控模型替身，验证无额外写入、无静默覆盖、旧授权不迁移到新提案。
