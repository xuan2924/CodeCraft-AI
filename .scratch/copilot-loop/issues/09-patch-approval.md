# P2-09：修改提案、Diff 与审批

**Type:** implementation
**Status:** needs-info
**Blocked by:** P2-08 只读 Copilot 任务
**Spec:** [第二阶段规格](../spec.md)

## What to build

在同一 Loop 中接入修改提案，交付默认逐次审批的整批 Diff、批准/拒绝、原子应用与结果回填。AI 文件创建/修改/删除/重命名复用第一阶段写入通道。

## 开工门槛

第一阶段达到 Dev Done（功能、L1 与代码审查完成，不含远程 CI 或重型验证），P2-08 及其上游提案 schema、检查点、审批排序与授权契约完成。读 [审批](../../../docs/design/approval.md)、[工作区](../../../docs/design/workspace-execution.md)、[Web IDE](../../../docs/design/web-ide.md)。

## Acceptance criteria

- [x] 提案固定工作区基线和完整变更，展示整批 Diff，默认 ask for approve；等待时保留批次位置及已完成结果，后续工具不执行。
- [x] 批准重新检查身份、归属、操作权、任务/演练状态、路径、容量、提案和基线；重复批准不重复应用。
- [x] 多文件整批成功或失败；基线变化使旧提案失效，不自动合并，不让旧批准授权新内容。
- [x] 拒绝可附理由，回填明确工具结果后继续当前任务，不自动终止整轮，也不允许无进展地反复提交相同被拒方案。
- [x] 应用与底座修订/回执同源，未知写入先对账；进程重启能恢复待审批及已应用结果，不重新生成或重放副作用。
- [x] AI 应用不覆盖本地草稿，明确提示协调；整批 Diff、结果及审计持久化并计入容量。
- [x] 确定性测试覆盖跨用户、旧页面、重复批准、拒绝后继续、基线冲突、批准/停止/到期竞争与写入丢响应；真实模型至少完成一个审批修改流程。

## Comments

本票先交付默认审批；auto 在 P2-12。必须具备本票自身的检查点与恢复，不将写入一致性留给综合验收。

### 授权下的实施取舍

- 修改工具采用 `propose_changes(expected_revision, changes)`，changes 沿用底座 CREATE/UPDATE/DELETE 与完整目标文本，重命名使用同一批次的 CREATE+DELETE。复用 `WorkspaceBatchCodec` 与 Go 原子写入，不另写 unified diff 解析/模糊匹配或应用引擎；代价是修改需要提供目标文件完整文本，超出单次模型输出范围的提案明确拒绝，不截断。Diff 由固定的修改前/后文本展示，不能把展示格式当写入协议。
- AI 单提案最多 32 个文件、192 KiB 参数；基线原文最多沿用工作区 10 MiB 内容上限。登记前预留 64 MiB，覆盖最坏 JSON 转义及元数据；登记完成后按实际持久化占用结算，批准时另走既有 FILE_BATCH 预留，等待人工审批不长期扣住整笔准备额度。原模型批次的收尾预留仍保持至结果配对完整。
- 待审批/待写入持久化为独立等待状态并释放 worker，不用阻塞线程维持审批，也不重新生成原批次。继续执行从原 assistant 消息和 tool_position 恢复；同场活动任务约束覆盖等待状态。
- 批准与既有 FILE_BATCH 意图在用户锁内同事务落盘，外部应用仍由 `WorkspaceWriteCoordinator` 在事务外执行。停止若遇到已准入但未确认的 AI 写入，复用工作区 RECONCILE/CloseGate 与原回执核对，不发第二次 Apply；直到写入结果及工具回执确定才终止父任务。相比另造提案专用提交协议，复用已验证的 Go 唯一发布点和栅栏排序；短暂收敛期间普通保存可能等待同一工作区协调，但不停止独立手动测试。
- 提案身份、完整内容、基线及决策幂等身份不可变；新基线/新内容必须生成新提案。拒绝后回填理由并继续原任务；同一已拒绝内容不会再次变成可批准提案。模型切换/删除不参与提案失效判断，后续模型请求仍遵循已确认边界。
- 新会话只有在对有效待审批提案作出新的显式决定、且通过当前操作权检查后，才更新原任务的后续调用授权。仅登录、浏览、原键读取历史决定不会重新授权。相比沿用已撤销会话导致审批后无法继续，或登录即自动恢复，此方案保持显式意图与当前授权一致。

### 实现、审查与验证收口

本票默认审批范围达到 Dev Done；auto、测试工具、steer 仍分别属于后续票。分诊 `Status` 不作为完成状态。

- V29/V30 持久化不可变提案、决策、写入关联、等待检查点与一次性批次进展记录。恢复从原 assistant/tool_position 继续，已完成前置读取不重放；批准和底座 FILE_BATCH 意图同事务，等待时释放 worker。工作区协调器独占发布与未知回执恢复，不另造应用通道。
- REST 提供有界元数据分页、完整不可变 Diff、轻量状态及幂等决定。Vue 使用已有 Monaco 的只读 Diff，一次仅挂载一个文件；完整文本不参与轮询。批准有整批确认与草稿/费用说明，不调用草稿保存；应用后刷新已有工作区观察，沿用编辑器冲突协调。丢响应后只重用原键，或从该不可变提案已决定/取消的事实确认审批受理；不会把 APPLYING 说成已应用。
- 自审覆盖需求和仓库规范：无事务内 RPC、无绕过原写通道、无模型配置变化导致旧提案误失效；未知写入不提前结束父任务，身份/操作权/路径/基线/容量均在准入边界复核。审查中补齐了刷新会话的显式重新授权、审批传输未知但服务端已决定时的 UI 收敛、完整 Diff 不被轮询重复下载，以及整批进展只记一次。无已知票内功能缺口。
- Java 全量单测及规范检查通过；Vue 150 项单测、类型检查、Lint 与生产构建通过；Node/Go quick、Linux 编译/vet、gofmt 通过。聚合 quick 曾因新增测试的局部变量引用编译失败，修复后单独复跑 Java 全量检查通过，未把那次失败的聚合命令记为通过；其余未变检查复用通过结果。
- 真实 PostgreSQL `CopilotPersistenceIT`：22 项普通测试通过、2 项收费测试默认跳过。新增覆盖前置读取/待审批重建 runner 后原批次续跑、重复批准、拒绝及重复被拒内容、跨用户/旧凭证/基线变化、容量拒绝、停止先后顺序、到期、选择模型删除、会话重新授权、已提交写入丢响应对账及提案删除。Go 边界是明确的确定性替身；多文件原子发布复用未改动底座及其既有证据，不据此宣称新的真实跨进程 exactly-once 验证。
- 单独启用真实 DeepSeek 审批流程通过：`deepseek-flash`、thinking OFF，共 4 次真实调用，依次读取、提出修改、人工审批后读取、最终回复；只有审批及写入回执确认后才继续。原始用量为 `1093/57/1150`、`1194/101/1295`、`1322/59/1381`、`1432/33/1465`（输入/输出/总量），未生成费用估值。供应商与 PostgreSQL 真实，Go 为确定性替身；凭证仅来自环境，临时连接在 finally 删除，未写入日志或提交。
- 完整真实 Java/Go/浏览器纵向链路按已安排的 P2-11 执行；本票结果不冒充该后续范围，也不另造通用 QA/生产验收欠账。
