# P2-14：恢复与竞争场景验收

**Type:** implementation
**Status:** needs-info
**Blocked by:** P2-12 自动审批模式；P2-13 运行中的 steer
**Spec:** [第二阶段规格](../spec.md)

## What to build

对已逐票交付的持久化和恢复做跨服务故障注入，补齐批准、停止、steer、到期、接管和身份撤销的组合边界。修复归属原功能，不另写旁路恢复器。

## 开工门槛

第一阶段全部验收；前置能力及 P2-02 恢复/授权契约完成。读 [接口恢复](../../../docs/design/api-events.md#保存与恢复)、[底座恢复协议](../../../docs/design/task-event-recovery.md)。

## Acceptance criteria

- [ ] 待审批跨 Java 重启恢复，保留完整批次、执行位置及已完成结果；处理前重新检查权限、版本和提案状态，不自动批准。
- [ ] 在 Go 发布前/后、响应丢失、Java 入库前/后故障时，按原请求对账；不重复应用、不把未知结果伪报未应用。
- [ ] 模型流中断或 Java 重启不自动重发收费请求；用户重试路径明确，浏览器重连只恢复观察，部分内容标不完整。
- [ ] 批准与停止/steer/到期按确认顺序处理，已应用保留，先失效则禁止写入；工具 ID/结果/推理字段不因恢复缺失或错配。
- [ ] 接管、刷新、会话撤销与后台 auto 的授权栅栏正确，旧页面不能继续操作，合法后台任务不因浏览器断线误停。
- [ ] 父任务停止与所属测试自然完成、未知执行、Go 重启一致；不误停独立测试，不提前释放隔离槽位。
- [ ] 真数据库、文件提交及 Docker 故障测试与模型替身测试分别记录，模型协议再由真实供应商票验证；不能以状态模型证明 exactly-once。

## Comments

这是综合恢复验收，不是持久化第一次进入实现。P2-08/09/10/12/13 必须已具备所属功能的检查点与回归证据。
